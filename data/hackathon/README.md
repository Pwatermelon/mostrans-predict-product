# Хакатон Московского транспорта · Предиктор задержек

## Датасет и правила формирования решения

Ваша задача — построить модель, которая по потоковой телеметрии транспорта **за 10–15 минут**
до события прогнозирует отклонение от графика и формирует файл `submission.csv` для
автоматической проверки. Метрика — **MAE** (средняя абсолютная ошибка прогноза задержки, сек).

---

## ⚠️ ГЛАВНОЕ: ответы по validate вам не выдаются

* `train/` и `test/` даны **с разметкой** (папка `labels/`) — на них вы обучаете и проверяете модель.
* Для периода `validate/` даны только **входные данные** (телеметрия + плановое расписание без
  факта) и `submission_template.csv`. **Фактических задержек по validate нет и не будет.**
* Проверка идёт по скрытому эталону (`ground_truth`) на стороне платформы. Вы **предсказываете**
  задержки по validate и загружаете `submission.csv`.

---

## 1. Что именно нужно предсказать

Прогнозная точка — пара `(tr_id, T)`: момент `T`, на который известна вся телеметрия ТС `tr_id`
вплоть до `T`. Нужно предсказать **фактическую задержку** (в секундах) на первой остановке этого
ТС, чьё **плановое** время прибытия попадает в окно `(T+10 мин, T+15 мин]`.

```
                     T (сейчас)         окно прогноза
   телеметрия ────────►│   +10 мин    ┌──────── +15 мин ┐
   ...GPS, скорость...  │              └──────┬──────────┘
                        │              целевая остановка → предсказать её задержку (сек)
```

* **Задержка = факт − план.** Положительная → опоздание, отрицательная → опережение.
* Целевая остановка и её плановое время уже даны (`target_stop_id`, `target_time_begin`) —
  предсказать нужно **величину задержки**.
* **Правило честности (анти-утечка):** при прогнозе для точки `T` используйте только данные,
  доступные на момент `T` — телеметрию с `event_time ≤ T` и подсказку `cur_dev_s`. Заглядывать
  в будущее нельзя.

## 3. Схема файлов

**traffic.csv** — телеметрия (разделитель `,`, UTF-8, ~12–15 c между точками):

| Колонка | Смысл |
|---|---|
| `tr_id` | ID транспортного средства (ключ связи с расписанием и разметкой) |
| `event_time` | время телеметрии (метка времени) |
| `location_valid` | достоверны ли координаты (`True`/`False`) |
| `lon`, `lat`, `alt` | долгота, широта, высота |
| `speed`, `heading` | скорость (км/ч), курс (°) |
| `unit_id`, `gps_time`, `receive_time`, `packet_id`, `device_event_id`, `is_hist_data` | служебные |

**schedule.csv** (в validate — `schedule_plan.csv` без факта):

| Колонка | Смысл |
|---|---|
| `tt_action_item_id` | ID планового прибытия на остановку (= `target_stop_id`) |
| `tr_id` | ID ТС |
| `time_begin` | **плановое** время прибытия |
| `time_fact_begin` | **фактическое** время прибытия (нет в validate) |
| `geom`, `building_address` | точка и адрес остановки |

**labels/*.csv** (train/test) и **validate/points.csv** — прогнозные точки:

| Колонка | Где | Смысл |
|---|---|---|
| `sample_id` | везде | уникальный ID прогнозной точки |
| `tr_id` | везде | ID ТС |
| `T` | везде | момент прогноза (используйте телеметрию `event_time ≤ T`) |
| `target_stop_id` | везде | ID целевой остановки |
| `target_time_begin` | везде | плановое время прибытия на целевую остановку |
| `cur_dev_s` | везде | **подсказка:** задержка на последней уже пройденной остановке (известна на T) |
| `target_delay_s` | только labels | **TARGET:** фактическая задержка на целевой остановке, сек |
| `target_class` | только labels | справочно: `early`/`ontime`/`late` (пороги −60 c / +120 c) |

## 4. Формат `submission.csv`

Разделитель `;`, UTF-8, заголовок обязателен. Ровно две колонки:

```
sample_id;prediction
131672_1767670500;120.0
122048_1767732000;45.0
130072_1767732000;-30.0
```

* `sample_id` — из `validate/points.csv` (нужны **все**, без дублей).
* `prediction` — прогноз задержки в **секундах** (число, знак важен: `+` опоздание, `−` опережение).

**Проще всего:** откройте `sample_submission.csv` (он уже в нужном формате и содержит все нужные
`sample_id`) и замените столбец `prediction` своими значениями.

## 5. Метрика

```
MAE      = mean(|факт − прогноз|)                        # секунды, меньше — лучше
mae_zero = mean(|факт|)                                   # прогноз «задержки нет»
score    = max(0, min(1, (mae_zero − MAE) / (mae_zero − MAE_TARGET)))   ∈ [0, 1]
```

`sample_submission.csv` — это baseline «прогноз = `cur_dev_s`»; он даёт **≈ 0.40**. Это «пол»,
который нужно превзойти обученной моделью (нулевой прогноз даёт `score = 0`).

## 6. Как работать

1. Соберите обучающую таблицу: соедините `labels/labels_train.csv` с признаками из
   `train/traffic.csv` (только `event_time ≤ T`!) и, при желании, из `train/schedule.csv`.
2. Обучите модель (CatBoost / бустинг / PyTorch — на ваш выбор), проверьте её на
   `labels/labels_test.csv`.
3. Для validate постройте те же признаки из `validate/traffic.csv` и `validate/points.csv`
   (момент `T`, `cur_dev_s`), предскажите задержку.
4. Возьмите `sample_submission.csv`, впишите свои прогнозы в `prediction`, отправьте на платформу.

## 7. Особенности данных

* Кодировка всех CSV — **UTF-8**; файлы данных — разделитель `,`, submission — `;`.
* Реальные задержки невелики (медиана ~25 c, максимум ~11 мин) — задача про точность в секундах.
* Не все ТС в `traffic.csv` имеют прогнозные точки: часть дана как дополнительный контекст
  (телеметрия без разметки) — можно использовать для self-supervised/калибровки.
* В `train` добавлены синтетические ТС (для объёма); `test`/`validate` — полностью реальные.
* Формат сабмита проверяется строго: колонки `sample_id;prediction`, без пропусков/дублей,
  полное покрытие всех `sample_id`.

## 8. Живой поток телеметрии (эмулятор NDTP)

CSV-файлы — это **уже раскодированная** телеметрия: строка `traffic.csv` соответствует
навигационной ячейке `G6CellNav00` протокола NDTP. Для обучения модели эмулятор не нужен —
достаточно CSV. Он нужен для **real-time части решения** (по ТЗ система должна принимать поток
телеметрии в реальном времени): эмулятор поднимает живой NDTP-поток, на котором вы отлаживаете
приём, парсинг пакетов и онлайн-инференс.

**Запуск** (подробности и REST-API — в `docs/Emulator-and-Telematic-Packets-Specification.md`):

```bash
docker load -i ndtp-telemetry-emulator.tar
docker run --rm -p 18080:18080 --add-host=host.docker.internal:host-gateway \
  --name ndtp-emu ndtp-telemetry-emulator:1.0
```

Затем `POST /api/config` (порт 18080) настраивает устройства и период отправки; эмулятор по TCP
шлёт NDTP-пакеты на ваш `targetHost:targetPort`.

**Соответствие полей `traffic.csv` ↔ `G6CellNav00`:**

| Колонка CSV | Поле NDTP | Преобразование |
|---|---|---|
| `event_time` / `gps_time` | `timestamp` | Unix-секунды → datetime |
| `lon` | `longitude` | `longitude / 1e7`, знак из `extraDopBit6` (E/W) |
| `lat` | `latitude` | `latitude / 1e7`, знак из `extraDopBit5` (N/S) |
| `alt` | `altitude` | метры |
| `speed` | `speedAvg` | км/ч |
| `heading` | `course` | градусы |
| `location_valid` | `extraDopBit7` | флаг достоверности координат |
| `unit_id` | `peerAddress` (`unitId`) | ID бортового терминала |

> Онлайн-часть — дополнительный контур поверх той же модели: офлайн обучаетесь на CSV, а на
> потоке эмулятора собираете те же признаки на момент `T` и выдаёте прогноз в реальном времени.
